# Consumer compiler API

The checker uses the consumer's own installed `typescript`. It parses configuration with `getParsedCommandLineOfConfigFile`, constructs a fresh `createProgram` and classifies `getPreEmitDiagnostics` objects by category, code and canonical file name. Configuration parsing follows the whole extends chain. TypeScript retains its original options object, including non-enumerable configuration metadata. No stdout diagnostic parser, language service or diagnostic-phase emulation remains.

Each matrix row now carries a `diagnostics` array besides `diagnostic_count` and the first `codes`: every error-category compiler diagnostic as `{code, file, line, column, message}` (warnings, suggestions and messages are not included). Strict parsers of the earlier row shape must accept that field. Messages are compiler text and can quote the consumer's source (identifiers, literals and type text), so treat them as source-derived content: do not publish them where the consumer's code would not be. Error-category diagnostics determine the verdict; exit_code is zero for a clean API result and one for errors. Full diagnostics retain file, line, column, code and flattened message. Paths and messages cross the worker boundary through an exclusive checker-owned JSON file; stdout is discarded. JSON strings preserve embedded newlines and diagnostic-like text.

SDK ownership is checked through each loaded file's own nearest named package.json, cached per canonical directory. Unnamed format-only metadata is skipped while finding the owning named root. Program SDK-specifier resolutions are included with their native usage modes. The selected root is the only supported SDK root: other canonical roots or unidentified SDK-specifier targets receive unsupported_project_shape, reason multiple_sdk_copies, named repo-relative roots and a dedupe remedy. Importing packages never confer their identity on nested declarations. Relative local packages and single-copy typesVersions resolutions retain native compiler diagnostics.

Stock 5.9.3 and 6.0.3 are tested against an independent direct API oracle and real tsc --build verdicts. Versions lacking createProgram, getPreEmitDiagnostics or getParsedCommandLineOfConfigFile receive compiler_unavailable. Programs lacking all usage-mode resolution APIs receive compiler_api_unavailable naming the source file. The pinned native 7.0.2 build compiler currently lacks the required APIs; its binary is never used as a text-based fallback and no other compiler is substituted.

Fresh programs never consume incremental state. The checker does not call emit or an incremental builder. References are refused as unsupported_project_shape before creating a Program: cached referenced declarations cannot prove either SDK bound. The refusal names both configs and recommends separate roots or flattened references. Standalone composite roots are checked without consuming referenced outputs. The logical root config is parsed at its original path; symlinks retain their relative origins, while confinement and identity comparisons use canonical paths. noEmit is enabled, trace/profile writers are inactive and host writeFile throws. Sources, configuration, caches and configured output destinations are preserved. Consumer code is never executed. See the [process inventory](sdk-contract-process-inventory.md) for filesystem and subprocess boundaries.
