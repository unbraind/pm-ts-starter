# Consumer compiler API

The checker uses the consumer's own installed `typescript`. It parses configuration with `getParsedCommandLineOfConfigFile`, constructs a fresh `createProgram` and classifies `getPreEmitDiagnostics` objects by category, code and canonical file name. Configuration parsing follows the whole extends chain. TypeScript retains its original options object, including non-enumerable configuration metadata. No stdout diagnostic parser, language service or diagnostic-phase emulation remains.

The matrix schema is unchanged. Error-category diagnostics determine the verdict; exit_code is zero for a clean API result and one for errors. Full diagnostics retain file, line, column, code and flattened message. Paths and messages cross the worker boundary through an exclusive checker-owned JSON file; stdout is discarded. JSON strings preserve embedded newlines and diagnostic-like text.

Ownership uses the Program's cached resolvedModule packageId, isExternalLibraryImport and realpath. forEachResolvedModule iterates unique source/specifier/usage-mode cache entries. Equivalent getResolvedModuleFromModuleSpecifier or getModeForUsageLocation/getResolvedModule APIs support other consumer versions. Type-reference identities also come from Program caches. Known canonical roots use ancestor-map lookup without filesystem or metadata discovery. There is no preProcessFile pass, synthetic identity import or resolveModuleName call. SDK declarations must belong to the selected canonical root and exact version; unknown or foreign identity receives a named isolation_refused. Ownership never walks package.json ancestors. Some classic typesVersions resolutions supply no packageId; these retain isolation_refused even when direct compilation succeeds.

Supported subset: a relative import into a nested local package may provide no resolved package identity. The copy inventories local manifest locations without reading metadata or assigning ownership. A loaded source under an unidentified package boundary receives unsupported_project_shape naming the file. Unused nested metadata, ordinary local declarations, installed dependencies remain supported. Import the package by its installed name or check it separately as its own root; broader relative-package support is deferred until identity can be obtained from the Program without synthetic resolution.

Stock 5.9.3 and 6.0.3 are tested against an independent direct API oracle and real tsc --build verdicts. Versions lacking createProgram, getPreEmitDiagnostics or getParsedCommandLineOfConfigFile receive compiler_unavailable. Programs lacking all usage-mode resolution APIs receive compiler_api_unavailable naming the source file. The pinned native 7.0.2 build compiler currently lacks the required APIs; its binary is never used as a text-based fallback and no other compiler is substituted.

Fresh programs never consume incremental state. The checker does not call emit or an incremental builder. References are refused as unsupported_project_shape before creating a Program: cached referenced declarations cannot prove either SDK bound. The refusal names both configs and recommends separate roots or flattened references. Standalone composite roots are checked without consuming referenced outputs. The logical root config is parsed at its original path; symlinks retain their relative origins, while confinement and identity comparisons use canonical paths. noEmit is enabled, trace/profile writers are inactive and host writeFile throws. Sources, configuration, caches and configured output destinations are preserved. Consumer code is never executed. See the [process inventory](sdk-contract-process-inventory.md) for filesystem and subprocess boundaries.
